# Web 漫畫修圖工作台開發計劃

狀態：規劃草案；本輪只建立獨立目錄及計劃，尚未實作或部署服務。

## 1. 目標與範圍

在 AutoDL 的 ComfyUI 鏡像中提供完整網頁工作台：建立具名專案、上傳圖片、預先編輯、執行三套工作流、比較結果、分區合成、導出成品。Web 服務監聽 `0.0.0.0:6008`。

`web/` 從第一天起作為可獨立搬出的工程：程式、前端、依賴清單、工作流配置、啟動腳本、測試及文件全部放在目錄內；執行時不引用上層倉庫程式，不使用 `../`、外部軟連結或修改 `sys.path` 接入母工程。

初版按單人工作台設計，保留多專案管理。暫按「同一份編輯後底圖與修補 Mask 分別送入三套工作流，產生三組候選結果」規劃；不是將三套工作流前後串接。實作前核對三套工程的實際輸入輸出。

「先改圖」初版包含純色填充、顏色選取、修補 Mask 添加／擦除、筆刷、矩形、撤銷／重做及自動保存；延續現有 F1 純色填充、F2 圖像修補的操作語意。套索、魔法棒及局部放大編輯列入後續增強。裁切、旋轉等改變座標的功能若需要，另加入同步變換圖片與 Mask 的設計。

## 2. 已確認的工程基礎

| 現有來源 | 可沿用能力 | Web 化處理 |
| --- | --- | --- |
| `detect_solid_inpaint_folder.py`、各 detector、`bubble_solid.py` | 文字偵測、純色分類、填色、修補 Mask | 將所需核心及其依賴整理進 Web 自有 Python 套件；移除固定模型路徑與 GUI 啟動依賴 |
| `project_store.py` | 兩類資料、人工修改保護、原子保存 | 沿用資料語意，新增 Web 專案 ID、修訂版本與穩定的內容雜湊 |
| `manga-flux-batch/batch_run.py`、`workflow_api.json` | FLUX Fill 的圖片／Mask 配對、ComfyUI 提交與結果收取 | 整理為通用執行適配器，工作流節點映射配置化 |
| `workflow_compare_ui.py` | 差異 Mask、來源分配、局部合成、羽化 | 將純影像運算移入不依賴 PySide6 的核心；網頁重建互動介面 |

目前倉庫找到一套 FLUX Fill 工作流，以及相應的 ComfyUI 編輯格式 JSON；尚未確認另外兩套工作流，不能將它們視為已接入。

已有桌面程式維持原有行為；Web 初期整理必要核心至自身目錄並記錄來源版本、保留授權說明。後續修改以 Web 內版本為準，避免依赖母工程的同步更新。

## 3. 鏡像與部署邊界

目標：[AutoDL ComfyUI 純淨版](https://www.autodl.art/app/market/64?v=87)。2026-09-09 查閱頁面時顯示：AutoDL 官方、應用版本 `v1`、應用 ID `2U7NVqfvXy:v1`，開機命令 `cd /root/ && bash start-comfyui.sh`。URL 的 `v=87` 不直接當作 ComfyUI 軟體版本。

實例內仍需核對：ComfyUI 版本與監聽地址、Python/CUDA 環境、模型、custom nodes、可持久化磁碟路徑、6008 是否占用，以及平台如何映射 6008 到外部入口。頁面本身不能證明這些已配置完成。

```text
瀏覽器
   │ 平台外部入口 → 實例 6008
   ▼
Web 服務：前端靜態檔案 + API + 圖片／導出存取
   ├── 專案資料與編輯保存
   ├── 持久化任務佇列 → 背景 Worker → 偵測與影像運算
   └── 背景 Worker → ComfyUI 內部 API → 三套工作流結果
```

ComfyUI 地址配置化，暫沿用現有批處理預設 `http://127.0.0.1:8188`，以實例檢查結果為準。瀏覽器透過 Web API 操作，不直接連使用者電腦的 localhost 或 ComfyUI 端口。

前端建置產物由 Python Web 服務提供，正式使用只需要一個 Web 入口。若平台要求路徑前綴，前端資源、API 與進度連線都支援配置前綴。服務內部 6008 與平台外部映射分開驗收。

## 4. 建議技術與獨立目錄

建議前端採 React + TypeScript + Canvas，後端採 FastAPI，影像核心採 Pillow／NumPy／OpenCV；實作時依鏡像環境鎖定相容版本。Web 使用獨立 Python 環境，避免與 ComfyUI 的依賴互相覆蓋，伺服器影像處理使用 headless 依賴。

任務與專案索引使用 SQLite，圖片、Mask、編輯資料以檔案保存；背景工作由獨立 Worker 執行，Web 重載不直接終止 GPU 任務。進度優先使用 SSE，另提供輪詢恢復方式。

以下為預計結構；目前僅建立本計劃文件：

```text
web/
├── DEVELOPMENT_PLAN.md
├── README.md
├── pyproject.toml
├── .env.example
├── .gitignore
├── frontend/                 # 獨立前端工程、依賴鎖定與建置
├── backend/
│   ├── api/                  # 專案、編輯、任務、比較、導出
│   ├── core/                 # 無 GUI 依賴的影像與合成核心
│   ├── adapters/             # 偵測器與 ComfyUI 接入
│   ├── jobs/                 # 任務佇列、Worker、恢復機制
│   └── storage/              # 檔案、SQLite、修訂管理
├── workflows/                # 三套 API JSON、節點映射、模型需求
├── scripts/                  # 安裝、檢查、建置、啟動
├── tests/
└── data/                     # 執行時建立，不提交 Git
    ├── app.sqlite3
    └── projects/<project_id>/
        ├── project.json
        ├── originals/        # 保留原始上傳
        ├── edits/            # 填色、Mask、人工修改記錄
        ├── inputs/<revision>/
        ├── runs/<run_id>/    # 每套工作流的參數、狀態及結果
        ├── compare/          # 差異 Mask 快取與像素來源分配
        └── exports/          # 成品、摘要與 ZIP
```

專案名稱與內部 ID 分離；保存原檔名和順序，同名檔案不互相覆蓋。專案內檔案引用全部相對於專案根目錄，預設資料目錄相對於 Web 工程根目錄，而非 shell 當前目錄。部署時可用 `DATA_DIR` 指向持久化磁碟、`MODEL_DIR` 指向模型目錄；外部資源必須明確配置，不能暗中依賴母工程。

## 5. 操作流程與關鍵規則

### A. 建立專案、上傳、編輯

- 輸入專案名稱，批量上傳圖片；顯示縮圖、自然排序、上傳進度及失敗原因。
- 建立原尺寸畫布，先正規化方向，保存上傳原件；前端縮放不改變原始像素座標。
- 接入現有偵測／純色分類能力，再人工調整 F1 填色與 F2 修補 Mask。第一個偵測器完成實例相容性驗證後接入，其他偵測器按需追加。
- 添加一類時移除另一類；擦除與人工修改在重新偵測後保留。
- 自動保存有明確的成功／失敗狀態，使用修訂號避免舊請求覆蓋新編輯。

### B. 三套工作流生成

- 使用同一修訂的「原圖 + 填色層」生成底圖，配套修補 Mask；空 Mask 頁面直接沿用底圖並標記跳過。
- 每套工作流獨立配置輸入節點、Mask 規則、參數、輸出節點、模型及 custom nodes 需求。以 API 格式 JSON 為執行來源。
- 支援選擇頁面、工作流與必要參數；可單頁試跑，再執行全部。
- 單 GPU 預設串行執行並協調偵測與生成的顯存使用，確認資源充足後才增加並行度。
- 保存輸入雜湊、工作流版本、參數、seed、ComfyUI prompt ID、輸出檔案及錯誤資訊。
- 工作狀態至少包含排隊、執行、成功、失敗、取消、待恢復；失敗可單項重試。
- 斷線或 Worker 重啟後先核對既有 prompt 狀態，無法確認的任務標記待恢復，避免盲目重複提交。
- 取消只作用於本專案任務；若 ComfyUI 無法安全定向中止正在執行的任務，停止後續排程並等待當前項結束。
- 執行中繼續編輯會產生新修訂；舊結果保留並提示過期，不與新底圖混用。

### C. 比較、選區合成

- 最左側顯示合成成品，右側最多並列三組候選，支援同步縮放、平移、原圖比較滑桿。
- 延續現有行為：按「工作流輸出與同修訂底圖」生成各自的差異 Mask，可調閾值、最小區域與擴張量。
- 差異 Mask 與生成用修補 Mask 分別保存；比較不以修補 Mask 取代工作流差異。
- 首次預設採用第一套成功結果的差異區域，介面清楚標示；其他區域沿用底圖。
- 支援整組採用、矩形與筆刷局部採用，以及局部保留底圖；各來源有不同顏色，選擇可撤銷／重做與保存。
- 來源分配使用原尺寸像素資料；縮圖僅供預覽。尺寸不同的輸出須有可驗證的逆變換才可還原，否则標記不可合成，不能直接拉伸對齊。
- 差異快取以底圖、工作流輸出雜湊和參數判定有效性；重算 Mask 不得默默清除人工採用記錄。

### D. 導出

- 單頁 PNG、全專案成品 ZIP，按原頁面順序與檔名映射輸出。
- 伺服器依原尺寸資料產生成品，預覽與導出使用相同合成規則，明確處理羽化邊界。
- 隨結果輸出 `selection.json`，記錄來源工作流、run ID、輸入修訂與合成設定。
- 另提供可重新開啟的專案封存，包含必要圖片、編輯、結果與像素來源分配；不僅保存摘要。
- 缺頁、失敗頁、過期結果或尚未完成的頁面在導出前明確列出，避免把部分成功顯示為全部完成。

## 6. 分階段開發與驗收

| 階段 | 開發內容 | 驗收標準 |
| --- | --- | --- |
| P0 環境與接口核對 | 檢查鏡像、6008 映射、三套工程、模型／節點，固定輸入輸出契約 | 三套工作流各完成同一張圖片的實例試跑；6008 外部可達 |
| P1 獨立骨架與專案管理 | Web/API/Worker、資料結構、建立專案、上傳、縮圖與重開 | 單獨複製 `web/` 後可安裝啟動；重啟後專案仍存在 |
| P2 圖片預處理與編輯 | 遷入核心、偵測、F1/F2、筆刷／矩形、保存與撤銷 | 同一測試頁的核心結果與現有程式一致；刷新後恢復編輯 |
| P3 工作流調度 | 先接通已知 FLUX，再接其餘兩套；進度、重試及恢復 | 三套均可從網頁執行；刷新不丟任務；重試不覆蓋既有結果 |
| P4 比較與合成 | 多面板、同步視圖、差異 Mask、來源分配與羽化 | 同頁不同區域可採用不同工作流；保存後可重開且成品一致 |
| P5 導出與鏡像整合 | PNG/ZIP/專案封存、啟動腳本、部署文件、完整驗收 | 在目標鏡像由上傳一路完成三套生成、比較、合成與下載 |
| P6 使用體驗增強 | 套索、魔法棒、局部放大、大批次縮圖優化 | 在完整流程穩定後按实际修圖需求驗收 |

P0 未齊備的其他工作流不阻止 P1/P2 與已知 FLUX 的開發，但 P3 和最終鏡像驗收必須使用三套真實工作流，不能用模擬輸出代替。

## 7. 驗證重點

- 核心回歸：兩類互斥、人工擦除保護、差異 Mask、局部來源分配、羽化與原尺寸導出。
- 整合：上傳配對、重名檔案、空 Mask、缺模型、錯誤輸出尺寸、任務重試及服務重啟恢復。
- 瀏覽器：縮放後筆刷座標正確、同步比較、保存失敗提示、斷線恢復、下載內容完整。
- 性能：以實際漫畫頁面驗證大圖記憶體與 GPU 顯存；前端按需讀取縮圖，後端避免一次解碼全專案圖片。
- 入口與檔案邊界：沿用平台可用的存取保護或配置工作台登入，限制上傳大小與類型，檔案存取限制於專案目錄。
- 獨立性：在沒有母工程的乾淨目錄中，只帶 `web/`、明確配置的模型與 ComfyUI，完成安裝啟動和小批次端到端驗收。
